## 1. Sistemas gestores de bases de datos

### 1.1. Base de datos y SGBD

- Una **base de datos (BD)** es una **colección organizada de datos relacionados**, almacenados con **mínima redundancia**, que pueden ser **compartidos** por varios usuarios y aplicaciones de forma **independiente** de los programas que los usan.
- Un **sistema gestor de bases de datos (SGBD)** (*DBMS*) es el **software** que permite **definir, crear, manipular, controlar y compartir** las bases de datos, actuando de intermediario entre los datos físicos y los usuarios o aplicaciones.
- **Sistema de base de datos** = base de datos + SGBD + aplicaciones + usuarios.

### 1.2. Ventajas frente a los sistemas de ficheros tradicionales

| Problema de los ficheros | Solución del SGBD |
|---|---|
| **Redundancia** de datos (el mismo dato en varios ficheros) | Datos **integrados** con redundancia mínima y controlada |
| **Inconsistencia** (copias con valores distintos) | Una sola versión; **integridad** |
| **Dependencia** entre datos y programas | **Independencia de datos** física y lógica |
| Dificultad de acceso y consulta | **Lenguajes de consulta** (SQL) |
| Acceso concurrente problemático | **Control de concurrencia** |
| Seguridad débil | **Control de acceso** centralizado |
| Recuperación difícil tras fallos | **Copias y recuperación** |

Inconvenientes de un SGBD: coste de licencias y hardware, complejidad, necesidad de personal especializado (DBA), punto crítico de fallo si no hay alta disponibilidad.

## 2. Funciones de un SGBD

| Función | Descripción | Lenguaje / mecanismo |
|---|---|---|
| **Definición de datos** | Crear y modificar la **estructura**: tablas, campos, tipos, restricciones, vistas, índices | **DDL** (*Data Definition Language*): CREATE, ALTER, DROP |
| **Manipulación de datos** | **Consultar**, insertar, modificar y borrar datos | **DML** (*Data Manipulation Language*): SELECT, INSERT, UPDATE, DELETE |
| **Control y seguridad** | Gestionar **usuarios, roles y privilegios**; cifrado; auditoría | **DCL** (*Data Control Language*): GRANT, REVOKE |
| **Integridad** | Garantizar que los datos son **correctos y coherentes** mediante **restricciones** (claves primarias y ajenas, NOT NULL, UNIQUE, CHECK) y disparadores | DDL, *triggers* |
| **Control de concurrencia** | Permitir el acceso **simultáneo** de muchos usuarios sin interferencias | **Transacciones**, **bloqueos**, **MVCC** |
| **Recuperación** | Restaurar la BD a un estado consistente tras un fallo | **Registro de transacciones (*log*)**, puntos de control, copias de seguridad |
| **Diccionario de datos (catálogo)** | Guardar los **metadatos**: descripción de tablas, columnas, tipos, usuarios, permisos, índices | *INFORMATION_SCHEMA*, vistas del sistema |
| **Optimización** | Elegir el **plan de ejecución** más eficiente para cada consulta | **Optimizador** de consultas |

## 3. Conceptos fundamentales

### 3.1. Arquitectura ANSI/SPARC de tres niveles

Propuesta por el comité **ANSI/X3/SPARC** en **1975**. Separa la visión de los datos en tres **niveles de abstracción** (esquemas):

| Nivel | Esquema | Qué describe | Para quién |
|---|---|---|---|
| **Externo** | **Esquemas externos** (subesquemas, **vistas**) | La parte de la base de datos que interesa a **cada usuario o aplicación** | Usuarios y aplicaciones |
| **Conceptual (lógico)** | **Esquema conceptual** (uno por BD) | La **estructura lógica global** de toda la base de datos: entidades, atributos, relaciones, restricciones, **sin detalles físicos** | Diseñador, DBA |
| **Interno (físico)** | **Esquema interno** | **Cómo se almacenan** físicamente los datos: ficheros, índices, bloques, métodos de acceso | SGBD, DBA |

Las **correspondencias (*mappings*)** entre niveles las mantiene el SGBD y proporcionan:

- **Independencia física**: se puede cambiar el **esquema interno** (añadir un índice, cambiar el disco o la organización de los ficheros) **sin afectar al esquema conceptual** ni a las aplicaciones.
- **Independencia lógica**: se puede cambiar el **esquema conceptual** (añadir una tabla o un atributo) **sin afectar a los esquemas externos** ni a las aplicaciones que no usan lo cambiado. Es más difícil de conseguir que la física.

### 3.2. Modelos de datos

Un **modelo de datos** es un conjunto de conceptos para describir la **estructura**, las **operaciones** y las **restricciones** de una base de datos.

| Nivel | Modelos |
|---|---|
| **Conceptuales** (alto nivel, independientes del SGBD) | **Entidad/Relación** (Chen, 1976) y E/R extendido; diagramas de clases **UML** |
| **Lógicos** (de implementación) | **Jerárquico**, **en red**, **relacional**, **orientado a objetos**, **objeto-relacional**, modelos NoSQL |
| **Físicos** | Estructuras de almacenamiento, índices |

### 3.3. Transacciones y propiedades ACID

Una **transacción** es una **secuencia de operaciones** que forman una **unidad lógica de trabajo**: o se ejecutan todas o ninguna (por ejemplo, traspasar una cama a otro paciente: liberar una y ocupar otra). Termina con **COMMIT** (confirmar) o **ROLLBACK** (deshacer).

Propiedades **ACID**:

| Propiedad | Significado |
|---|---|
| **Atomicidad** | **Todo o nada**: si una operación falla, se deshacen todas |
| **Consistencia** | La transacción lleva la BD de un **estado válido a otro estado válido**, respetando las restricciones de integridad |
| **Aislamiento (*Isolation*)** | Las transacciones concurrentes **no interfieren** entre sí: cada una se ejecuta como si fuera la única |
| **Durabilidad** | Una vez confirmada (COMMIT), la transacción **persiste** aunque haya un fallo posterior (gracias al registro de transacciones) |

### 3.4. Control de concurrencia

**Anomalías** que pueden producirse con transacciones concurrentes:

| Anomalía | Descripción |
|---|---|
| **Actualización perdida** | Dos transacciones modifican el mismo dato y una sobrescribe a la otra |
| **Lectura sucia** (*dirty read*) | Se lee un dato modificado por otra transacción **aún no confirmada** (que puede deshacerse) |
| **Lectura no repetible** | Se lee un dato dos veces en la misma transacción y da **valores distintos** porque otra lo modificó y confirmó entre medias |
| **Lectura fantasma** (*phantom*) | Una consulta repetida devuelve **filas nuevas** (o desaparecidas) porque otra transacción insertó o borró |

**Niveles de aislamiento** (estándar SQL):

| Nivel | Lectura sucia | No repetible | Fantasma |
|---|---|---|---|
| **READ UNCOMMITTED** | Posible | Posible | Posible |
| **READ COMMITTED** (por defecto en Oracle, PostgreSQL y SQL Server) | Evitada | Posible | Posible |
| **REPEATABLE READ** (por defecto en MySQL InnoDB) | Evitada | Evitada | Posible |
| **SERIALIZABLE** | Evitada | Evitada | Evitada (máximo aislamiento, menor concurrencia) |

**Técnicas**:

- **Bloqueos** (*locks*): **compartidos** (de lectura) y **exclusivos** (de escritura), con distinta **granularidad** (fila, página, tabla). El **bloqueo en dos fases** (2PL) garantiza la serializabilidad. Riesgo de **interbloqueos** (*deadlocks*), que el SGBD detecta y resuelve abortando una transacción.
- **Control multiversión (MVCC)**: cada transacción ve una **instantánea** consistente de los datos; los lectores no bloquean a los escritores (PostgreSQL, Oracle, MySQL InnoDB).
- **Marcas de tiempo** (*timestamps*) y control **optimista**.

### 3.5. Recuperación

- El **registro de transacciones** (*log*, *redo log*, *WAL: write-ahead log*) anota los cambios **antes** de aplicarlos a los datos.
- Tras una caída, el SGBD **rehace** (*redo*) las transacciones confirmadas y **deshace** (*undo*) las no confirmadas.
- **Puntos de control** (*checkpoints*) para acelerar la recuperación.
- Fallos posibles: de transacción, del sistema (caída), del soporte (disco): este último exige **copias de seguridad**.

## 4. Arquitecturas de los SGBD

| Arquitectura | Descripción |
|---|---|
| **Centralizada** | SGBD y datos en un único equipo (mainframe) |
| **Cliente/servidor** | El **servidor de BD** gestiona los datos y los **clientes** (aplicaciones) envían peticiones por la red. En **2 capas** (cliente → BD) o **3 o más capas** (cliente → servidor de aplicaciones → BD), la habitual en aplicaciones web y sanitarias |
| **Distribuida** | Los datos se reparten entre **varios nodos** conectados, pero el usuario los ve como una sola BD (**transparencia de distribución**). Técnicas: **fragmentación** (horizontal, vertical) y **réplica**; protocolo de **confirmación en dos fases (2PC)** |
| **Paralela** | Varios procesadores y discos para acelerar (*shared nothing*, *shared disk*) |
| **En clúster** | Varias instancias sobre el mismo almacenamiento para **alta disponibilidad** (Oracle RAC) |
| **En la nube (DBaaS)** | La base de datos como servicio gestionado (Azure SQL Database, Amazon RDS, Cloud SQL) |
| **En memoria** | Datos en RAM para máxima velocidad (SAP HANA, Redis) |

Componentes internos de un SGBD: **procesador de consultas** (analizador, optimizador, ejecutor), **gestor de transacciones**, **gestor de almacenamiento** (*buffer*, ficheros, índices), **gestor de recuperación**, **diccionario de datos**.

## 5. Tipos de SGBD

::diagrama nosql-tipos

| Tipo | Estructura | Ejemplos |
|---|---|---|
| **Jerárquico** | **Árbol**: cada registro hijo tiene un único padre (relaciones 1:N) | IBM **IMS** (años 60) |
| **En red** | **Grafo**: un registro puede tener varios padres (relaciones N:M); modelo **CODASYL** | IDMS |
| **Relacional** | **Tablas** (relaciones) con filas y columnas; consultas con **SQL**; basado en el modelo de **Codd (1970)** | **Oracle Database**, **Microsoft SQL Server**, **PostgreSQL**, **MySQL**, **MariaDB**, IBM Db2, SQLite |
| **Orientado a objetos** | Almacena **objetos** con su identidad, herencia y métodos; estándar **ODMG** (lenguaje **OQL**) | db4o, ObjectDB, Versant |
| **Objeto-relacional** | Relacional ampliado con **tipos definidos por el usuario**, herencia de tablas y métodos (SQL:1999) | **PostgreSQL**, Oracle |
| **NoSQL** | Modelos no relacionales, **esquema flexible**, escalado horizontal (tema 22) | **MongoDB**, **Redis**, **Cassandra**, **Neo4j** |
| **NewSQL** | Relacional (SQL y ACID) con escalabilidad horizontal | CockroachDB, Google Spanner |
| **Analíticos / almacenes de datos** | Orientados a consultas masivas (OLAP), almacenamiento **columnar** | Snowflake, Amazon Redshift, ClickHouse |

**OLTP frente a OLAP**:

| | **OLTP** (*Online Transaction Processing*) | **OLAP** (*Online Analytical Processing*) |
|---|---|---|
| Uso | Operaciones diarias (citas, ingresos, recetas) | Análisis, informes, cuadros de mando |
| Operaciones | Muchas transacciones pequeñas de lectura y escritura | Consultas complejas de lectura sobre grandes volúmenes |
| Diseño | **Normalizado** | **Desnormalizado**: modelo **en estrella** o **copo de nieve** (tablas de **hechos** y **dimensiones**), **cubos** |
| Ejemplo | Base de datos de la historia clínica | ***Data warehouse*** de actividad asistencial (CMBD) |

El proceso **ETL** (extracción, transformación y carga) lleva los datos de los sistemas OLTP al *data warehouse*. Un ***data lake*** almacena datos en bruto de cualquier formato.

## 6. Administración de sistemas de gestión de bases de datos

### 6.1. El administrador de bases de datos (DBA)

Funciones del **DBA**:

- **Instalación, configuración y actualización** del SGBD (versiones y parches).
- **Diseño físico** y gestión del **almacenamiento**: *tablespaces*, ficheros de datos, crecimiento, particionado.
- **Gestión de usuarios, roles y privilegios** (seguridad).
- **Copias de seguridad y recuperación**.
- **Supervisión y optimización del rendimiento** (*tuning*).
- **Alta disponibilidad** y recuperación ante desastres.
- **Mantenimiento**: estadísticas, reconstrucción de índices, comprobación de integridad.
- **Auditoría** y cumplimiento normativo (RGPD, ENS).
- **Migraciones** y cambios de esquema; coordinación con los desarrolladores.

(El **administrador de datos** o *data steward* se ocupa de los aspectos lógicos y de gobierno del dato; el DBA, de los técnicos).

### 6.2. Copias de seguridad

| Tipo | Qué copia | Restauración |
|---|---|---|
| **Completa (total)** | **Toda** la base de datos | Solo la última completa |
| **Incremental** | Los cambios desde la **última copia de cualquier tipo** (completa o incremental) | La completa + **todas** las incrementales posteriores (más lenta de restaurar, más rápida de hacer) |
| **Diferencial** | Los cambios desde la **última copia completa** (va creciendo cada día) | La completa + **la última** diferencial |
| **Del registro de transacciones** | El *log* de transacciones | Permite la **recuperación a un momento concreto** (*point-in-time recovery*) |

Otros conceptos:

- **En caliente** (*online*, con la BD en servicio) y **en frío** (*offline*, con la BD parada).
- **Lógicas** (exportación de los datos y estructuras: pg_dump, mysqldump, Data Pump de Oracle) y **físicas** (copia de los ficheros: **RMAN** de Oracle, backup nativo de SQL Server).
- **RPO** (*Recovery Point Objective*): **cuántos datos** se pueden perder como máximo (por ejemplo, 15 minutos). **RTO** (*Recovery Time Objective*): **cuánto tiempo** como máximo puede tardar la recuperación.
- **Regla 3-2-1**, copias **cifradas** y fuera del sitio, y **pruebas periódicas de restauración** (una copia que no se ha probado no es fiable).

### 6.3. Rendimiento y optimización

- **Índices** adecuados en las columnas de búsqueda, unión y ordenación (sin excederse: ralentizan las escrituras).
- Análisis de los **planes de ejecución** (EXPLAIN) y reescritura de consultas lentas.
- **Estadísticas** actualizadas para el optimizador.
- **Particionado** de tablas grandes (por fechas, por rangos).
- Configuración de la **memoria** (*buffer pool*, caché) y del almacenamiento.
- **Pool de conexiones** en las aplicaciones.
- Monitorización: bloqueos, esperas, consultas más costosas (AWR en Oracle, Query Store en SQL Server, pg_stat_statements en PostgreSQL).

### 6.4. Alta disponibilidad y recuperación ante desastres

| Técnica | Descripción | Ejemplos |
|---|---|---|
| **Réplica** | Copia de los datos en otro servidor, **síncrona** (sin pérdida, más lenta) o **asíncrona** (más rápida, posible pérdida) | Réplica de PostgreSQL y MySQL |
| **Servidor en espera (*standby*)** | Copia continuamente actualizada que toma el control si falla el principal (**conmutación por error**, *failover*) | **Oracle Data Guard**, **SQL Server Always On**, *log shipping* |
| **Clúster** | Varios nodos que comparten la carga o se respaldan | **Oracle RAC**, clúster de conmutación por error de Windows |
| **Copias en otra ubicación** | Para desastres | Centro de respaldo |

## 8. Técnicas y procedimientos de seguridad

### 8.1. Control de acceso

- **Autenticación** de los usuarios: del propio SGBD, integrada con el **directorio** (Active Directory, LDAP, Kerberos) o mediante certificados.
- **Autorización** mediante **privilegios** sobre objetos (SELECT, INSERT, UPDATE, DELETE, EXECUTE) y del sistema, concedidos con **GRANT** y retirados con **REVOKE**; agrupación en **roles**.
- **Principio de mínimo privilegio**: cada usuario y aplicación con los permisos imprescindibles. Las aplicaciones no deben conectarse con cuentas de administrador (sa, sys, root).
- **Vistas** para mostrar solo determinadas columnas o filas.
- **Seguridad a nivel de fila** (*Row-Level Security*, Virtual Private Database en Oracle): cada usuario ve solo las filas que le corresponden (por ejemplo, los pacientes de su centro).
- Separación de funciones entre DBA, desarrolladores y auditores.

### 8.2. Protección de los datos

- **Cifrado en reposo**: **TDE** (*Transparent Data Encryption*: cifra los ficheros de datos, el *log* y las copias sin cambiar las aplicaciones; Oracle, SQL Server, MySQL), cifrado de columnas concretas, cifrado de las copias.
- **Cifrado en tránsito**: conexiones **TLS** entre aplicaciones y SGBD.
- **Enmascaramiento** de datos (estático o dinámico) y **seudonimización/anonimización** para usar datos reales en **entornos de desarrollo y pruebas** sin exponer datos de pacientes (exigencia del RGPD).
- **Gestión segura de las claves** (HSM, almacenes de claves).

### 8.3. Auditoría y monitorización

- **Auditoría** de accesos y operaciones (quién consultó o modificó qué y cuándo), especialmente sobre datos de salud, que son **categoría especial** del RGPD; en el ENS, registro de la actividad.
- Herramientas de **Database Activity Monitoring (DAM)** e integración con el **SIEM**.
- Alertas ante accesos anómalos (consultas masivas, horarios inusuales).

### 8.4. Seguridad del servidor y de las aplicaciones

- **Bastionado** del SGBD: eliminar cuentas y bases de datos de ejemplo, cambiar contraseñas por defecto, desactivar funciones innecesarias, aplicar los **parches** de seguridad, guías CCN-STIC o CIS Benchmarks.
- Aislamiento en la **red** (las BD en una red interna, nunca expuestas a Internet; cortafuegos).
- Prevención de la **inyección SQL**: **consultas parametrizadas** o sentencias preparadas, validación de las entradas, procedimientos almacenados, cuentas con mínimos privilegios.
- **Copias de seguridad** protegidas frente a ransomware (inmutables o desconectadas).
- Cumplimiento del **RGPD** (protección de datos desde el diseño, registro de actividades de tratamiento, brechas) y del **ENS**.

## 9. Ideas que más caen en el examen

> - SGBD: **definir, manipular, controlar y compartir** datos. Ventajas: menos redundancia, integridad, **independencia**, concurrencia, seguridad, recuperación.
> - **DDL** (CREATE, ALTER, DROP), **DML** (SELECT, INSERT, UPDATE, DELETE), **DCL** (GRANT, REVOKE).
> - **ANSI/SPARC (1975)**: niveles **externo, conceptual e interno**. **Independencia física** (cambiar el interno sin afectar al conceptual) y **lógica** (cambiar el conceptual sin afectar a los externos).
> - **ACID**: **atomicidad, consistencia, aislamiento, durabilidad**.
> - Anomalías: **lectura sucia, no repetible, fantasma**. **SERIALIZABLE** = máximo aislamiento.
> - Tipos: **jerárquico** (IMS), **en red** (CODASYL), **relacional** (Codd, 1970), **orientado a objetos** (ODMG/OQL), **objeto-relacional**, **NoSQL**.
> - **OLTP** (transaccional, normalizado) frente a **OLAP** (analítico, estrella, *data warehouse*, ETL).
> - Copias: **completa**; **incremental** (desde la última de cualquier tipo); **diferencial** (desde la última completa). **RPO** = datos que se pueden perder; **RTO** = tiempo de recuperación.
> - Alta disponibilidad: **Data Guard**, **Always On**, **RAC**, réplicas.
> - Herramientas: **SSMS** (SQL Server), **SQL Developer** y **RMAN** (Oracle), **pgAdmin** (PostgreSQL), **Workbench** (MySQL).
> - Seguridad: **mínimo privilegio**, roles, vistas, **TDE**, TLS, **enmascaramiento**, auditoría, **consultas parametrizadas** contra la inyección SQL.
