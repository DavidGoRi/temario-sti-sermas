## 1. La interacción con los sistemas de gestión de bases de datos

Los usuarios y las aplicaciones se comunican con un SGBD de varias formas:

| Tipo de usuario | Forma de interacción |
|---|---|
| **Usuario final ocasional** | Formularios, informes y herramientas de consulta gráficas (QBE, *query builders*, herramientas de BI) |
| **Usuario final paramétrico** | Aplicaciones con transacciones predefinidas (la aplicación de citación) |
| **Programador de aplicaciones** | **Lenguajes de consulta** (SQL) incrustados en programas o a través de **interfaces de acceso a datos** (APIs como ODBC y JDBC) o **motores de persistencia** (ORM) |
| **Administrador (DBA)** | Herramientas de administración, línea de órdenes, DDL y DCL |

Formas de usar SQL desde los programas:

- **SQL interactivo**: el usuario escribe las sentencias directamente en una herramienta (SSMS, SQL Developer, psql).
- **SQL embebido (incrustado)**: sentencias SQL dentro del código de un lenguaje anfitrión (COBOL, C), que un **precompilador** traduce a llamadas (Pro*C de Oracle, ECPG de PostgreSQL).
- **SQL dinámico**: la sentencia se construye en tiempo de ejecución (con riesgo de **inyección SQL** si no se usan parámetros).
- **Llamadas a una API** de acceso a datos (ODBC, JDBC, ADO.NET).
- **Procedimientos almacenados** y funciones dentro del propio SGBD (**PL/SQL** en Oracle, **T-SQL** en SQL Server, **PL/pgSQL** en PostgreSQL), invocados por las aplicaciones.

## 2. Lenguajes de interrogación de bases de datos

### 2.1. Clasificación

| Tipo | Descripción | Ejemplos |
|---|---|---|
| **Procedimentales** | El usuario indica **qué** datos quiere y **cómo** obtenerlos (la secuencia de operaciones) | **Álgebra relacional** |
| **No procedimentales (declarativos)** | El usuario indica **qué** quiere, y el SGBD decide cómo | **Cálculo relacional**, **SQL**, **QBE** |
| **Gráficos** | Consultas construidas visualmente | **QBE**, generadores de consultas de Access |

### 2.2. Álgebra relacional

Propuesta por **Codd**, es un lenguaje **procedimental** formado por **operadores** que toman relaciones (tablas) como entrada y devuelven nuevas relaciones (propiedad de **cierre**).

| Operador | Símbolo | Qué hace | Equivalente SQL |
|---|---|---|---|
| **Selección** | σ (sigma) | Elige las **filas** que cumplen una condición | WHERE |
| **Proyección** | π (pi) | Elige **columnas** (y elimina duplicados) | SELECT columnas (DISTINCT) |
| **Unión** | ∪ | Filas de una u otra relación (compatibles) | UNION |
| **Diferencia** | − | Filas de la primera que no están en la segunda | EXCEPT / MINUS |
| **Producto cartesiano** | × | Combina cada fila de una con todas las de la otra | CROSS JOIN |
| **Renombrado** | ρ (rho) | Cambia el nombre de una relación o atributo | AS |
| **Intersección** (derivado) | ∩ | Filas comunes | INTERSECT |
| **Combinación o reunión (*join*)** (derivado) | ⋈ | Producto cartesiano + selección por una condición (**natural**, **theta**, **equi**, **externa**) | JOIN |
| **División** (derivado) | ÷ | Filas relacionadas con **todas** las de otra relación («pacientes vacunados de todas las vacunas») | NOT EXISTS anidados |

Los cinco operadores **básicos** (o primitivos) son **selección, proyección, unión, diferencia y producto cartesiano** (con el renombrado); los demás se derivan de ellos.

### 2.3. Cálculo relacional

Lenguaje **declarativo** basado en la **lógica de predicados**:

- **Cálculo relacional de tuplas** (Codd): las variables recorren **filas**. Ejemplo: { t | t ∈ Paciente ∧ t.edad > 65 }.
- **Cálculo relacional de dominios**: las variables recorren **valores de los atributos**; es la base de QBE.

Un lenguaje es **relacionalmente completo** si puede expresar todo lo que expresa el álgebra relacional (SQL lo es).

### 2.4. SQL

**SQL** (*Structured Query Language*) es el **lenguaje estándar** de las bases de datos relacionales, desarrollado por **IBM** en los años 70 (SEQUEL, para System R) y normalizado por **ANSI** e **ISO** (SQL-86, SQL-89, **SQL-92**, SQL:1999, SQL:2003, SQL:2011, **SQL:2016**, SQL:2023). Es **declarativo** y tiene sublenguajes DDL, DML, DCL y TCL. Se desarrolla en el tema 22. Cada SGBD añade **extensiones** procedimentales: **PL/SQL**, **T-SQL**, PL/pgSQL.

### 2.5. QBE (*Query By Example*)

- Creado por **Moshé Zloof** en **IBM** (años 70), basado en el cálculo relacional de dominios.
- El usuario formula la consulta **rellenando una plantilla gráfica** de la tabla con **ejemplos** de los valores que busca y condiciones, sin escribir código.
- Lo popularizaron las herramientas de diseño de consultas de **Microsoft Access** y otras herramientas de usuario final.

### 2.6. Otros lenguajes de consulta

| Lenguaje | Para qué |
|---|---|
| **OQL** (*Object Query Language*) | Bases de datos orientadas a objetos (estándar ODMG) |
| **JPQL / HQL** | Consultas sobre entidades en JPA / Hibernate (tema 21.4) |
| **XPath** y **XQuery** | Documentos **XML** |
| **SPARQL** | Datos **RDF** (web semántica, datos enlazados, terminologías como SNOMED en formato RDF) |
| **Cypher** (Neo4j) y **GQL** (estándar ISO de grafos, 2024) | Bases de datos de **grafos** |
| **CQL** | Cassandra (sintaxis parecida a SQL) |
| **Lenguaje de consulta de MongoDB** (MQL) | Documentos JSON |
| **MDX** y **DAX** | Cubos OLAP y modelos de Power BI |
| **GraphQL** | Consulta de **APIs** (no de bases de datos): el cliente pide exactamente los campos que necesita |

## 3. Interfaces para el acceso a datos

> El temario dice «OJDB, JDBD y otros»: se refiere a **ODBC** y **JDBC**, las dos interfaces estándar más conocidas.

### 3.1. ODBC (*Open Database Connectivity*)

- Desarrollada por **Microsoft** (1992), basada en la especificación **SQL/CLI** (*Call Level Interface*) del X/Open e ISO.
- Es una **API en C**, **independiente del lenguaje y del SGBD**: la aplicación usa las mismas funciones y el **driver ODBC** de cada SGBD traduce las llamadas.
- Arquitectura:
  1. **Aplicación**: llama a las funciones ODBC (conectar, ejecutar SQL, obtener resultados).
  2. **Administrador de controladores (*Driver Manager*)**: carga el driver adecuado (en Windows, «Orígenes de datos ODBC», odbcad32.exe; en Linux, unixODBC).
  3. **Controlador (*driver*) ODBC** del SGBD concreto.
  4. **Origen de datos** (la base de datos).
- La conexión se configura mediante un **DSN** (*Data Source Name*): de **usuario**, de **sistema** o de **archivo**; o con una cadena de conexión sin DSN.
- Muy usada para conectar herramientas de ofimática, informes y BI (Excel, Power BI, Crystal Reports) con cualquier base de datos.

### 3.2. JDBC (*Java Database Connectivity*)

- **API estándar de Java** (paquetes java.sql y javax.sql), creada por Sun en **1997**, para acceder a bases de datos **relacionales** desde Java de forma independiente del SGBD.
- **Clases e interfaces principales**:

| Elemento | Función |
|---|---|
| **DriverManager** / **DataSource** | Obtener conexiones (DataSource permite *pool* de conexiones y es lo recomendado en servidores) |
| **Connection** | Conexión con la base de datos; gestiona las **transacciones** (setAutoCommit, commit, rollback) |
| **Statement** | Ejecutar sentencias SQL estáticas |
| **PreparedStatement** | Sentencias **precompiladas con parámetros** (`?`): más eficientes y **seguras frente a la inyección SQL** |
| **CallableStatement** | Llamar a **procedimientos almacenados** |
| **ResultSet** | Conjunto de **resultados** de una consulta, que se recorre fila a fila |
| **SQLException** | Errores |

- La conexión se indica con una **URL JDBC**: `jdbc:postgresql://servidor:5432/hospital`, `jdbc:oracle:thin:@servidor:1521/SERVICIO`.
- **Tipos de driver JDBC**:

| Tipo | Nombre | Funcionamiento |
|---|---|---|
| **1** | Puente **JDBC-ODBC** | Traduce JDBC a ODBC (obsoleto; eliminado en Java 8) |
| **2** | API nativa | Usa la biblioteca cliente nativa del SGBD |
| **3** | Protocolo de red (*middleware*) | Habla con un servidor intermedio que accede a la BD |
| **4** | **Java puro (*thin*)** | Implementa en Java el **protocolo de red del SGBD**; no necesita software adicional. **Es el más usado** |

### 3.3. Otras interfaces

| Interfaz | Plataforma | Notas |
|---|---|---|
| **OLE DB** | Microsoft (COM) | Acceso a fuentes relacionales y no relacionales |
| **ADO** | Microsoft (COM, Visual Basic clásico, ASP) | Capa de alto nivel sobre OLE DB |
| **ADO.NET** | **.NET** | Proveedores de datos (SqlClient, Npgsql, Oracle Data Provider): Connection, Command, DataReader, DataSet (modo **desconectado**), DataAdapter |
| **PDO** (*PHP Data Objects*) | PHP | Interfaz única con sentencias preparadas |
| **DB-API (PEP 249)** | Python | psycopg (PostgreSQL), cx_Oracle/oracledb, pyodbc |
| **R2DBC** | Java reactivo | Acceso no bloqueante |
| **APIs REST / OData** | Web | Exponer los datos como servicios web (OData es un estándar OASIS para APIs de datos) |

**Pool de conexiones**: abrir una conexión a la BD es costoso; los servidores de aplicaciones mantienen un **conjunto de conexiones abiertas** que se reutilizan (HikariCP, configuraciones de los servidores Java y .NET).

## 4. Los motores de persistencia

### 4.1. El problema del desajuste objeto-relacional

Las aplicaciones se programan con **objetos** (clases, herencia, referencias, colecciones), pero los datos se guardan en **tablas** (filas, columnas, claves ajenas). La diferencia entre ambos modelos se llama **desajuste de impedancia objeto-relacional** (*object-relational impedance mismatch*): herencia, identidad, asociaciones bidireccionales, granularidad y navegación no tienen equivalente directo en el modelo relacional.

### 4.2. ORM (*Object-Relational Mapping*)

Un **motor de persistencia** o **ORM** es una capa de software que **mapea automáticamente los objetos a tablas** y viceversa, de modo que el programador trabaja con objetos y el ORM genera el SQL.

**Funcionalidades**:

- **Mapeo** de clases a tablas, atributos a columnas, relaciones (1:1, 1:N, N:M) a claves ajenas y tablas intermedias, y **herencia** (tabla única, tabla por subclase, tabla por clase concreta). Se define con **anotaciones** en el código o con ficheros **XML**.
- Operaciones **CRUD** (*Create, Read, Update, Delete*) sin escribir SQL.
- **Lenguaje de consulta orientado a objetos** (JPQL, HQL, LINQ) además de SQL nativo.
- Gestión de **transacciones** y del **contexto de persistencia** (seguimiento de los cambios de los objetos: *dirty checking*).
- **Carga perezosa** (*lazy loading*: los datos relacionados se cargan cuando se usan) o **ansiosa** (*eager*).
- **Caché** de primer y segundo nivel.
- **Independencia del SGBD** (dialectos) y generación o validación del esquema.
- Control de concurrencia **optimista** (versionado).

**Ventajas**: más **productividad**, menos código repetitivo, código más mantenible y portable, menos errores de SQL e inyección (consultas parametrizadas). **Inconvenientes**: curva de aprendizaje, **rendimiento** si se usa mal (el problema de las **N+1 consultas**), menos control sobre el SQL generado.

### 4.3. Principales motores de persistencia

| Herramienta | Plataforma | Características |
|---|---|---|
| **JPA / Jakarta Persistence** | Java | **Especificación estándar** de persistencia de Java (antes Java Persistence API). Anotaciones **@Entity**, @Table, **@Id**, @Column, @OneToMany, @ManyToOne; **EntityManager**; lenguaje **JPQL** |
| **Hibernate** | Java | El ORM más usado; **implementación de JPA** (con extensiones propias y lenguaje **HQL**). Integrado con **Spring Data JPA** |
| EclipseLink | Java | Implementación de referencia de JPA |
| **MyBatis** | Java | Mapeador de **SQL**: el programador escribe el SQL y MyBatis mapea los resultados a objetos (más control) |
| **Entity Framework (EF Core)** | **.NET** | ORM de Microsoft; consultas con **LINQ**; *migrations* |
| NHibernate, Dapper (micro-ORM) | .NET | — |
| **Doctrine** / Eloquent | PHP (Symfony / Laravel) | — |
| **SQLAlchemy** / ORM de **Django** | Python | — |
| Sequelize, TypeORM, Prisma | JavaScript/TypeScript (Node.js) | — |
| Active Record | Ruby on Rails | Patrón **Active Record** (el objeto sabe guardarse a sí mismo) |

Patrones de diseño relacionados: **DAO** (*Data Access Object*: encapsula el acceso a datos), **Repository**, **Unit of Work**, **Active Record** y **Data Mapper**.

## 5. La indexación de la información y los motores de búsqueda

### 5.1. Índices en las bases de datos

Un **índice** es una **estructura auxiliar** que permite **localizar rápidamente** las filas sin recorrer toda la tabla, como el índice de un libro.

| Tipo de índice | Características | Uso |
|---|---|---|
| **Árbol B / B+** | Equilibrado, multinivel; en B+ los datos están en las **hojas enlazadas**. Permite búsquedas por **igualdad y por rango** y recorridos ordenados | **El índice por defecto** en casi todos los SGBD |
| **Hash** | Función hash sobre la clave | Solo búsquedas por **igualdad** exacta |
| **Bitmap** | Un mapa de bits por cada valor distinto | Columnas de **baja cardinalidad** (sexo, provincia) en **almacenes de datos**; malo para muchas escrituras |
| **Agrupado (*clustered*)** | **Ordena físicamente** la tabla según la clave; **solo uno por tabla** (en SQL Server, normalmente la clave primaria) | Rangos, clave primaria |
| **No agrupado (*nonclustered*)** | Estructura separada con punteros a las filas; varios por tabla | Búsquedas por otras columnas |
| **Compuesto** | Sobre varias columnas (importa el **orden** de las columnas) | Búsquedas combinadas |
| **Único** | Impide valores repetidos | Claves alternativas (DNI, NHC) |
| **De cobertura** (*covering*) | Incluye todas las columnas que necesita la consulta | Evita acceder a la tabla |
| **De texto completo (*full-text*)** | Índice invertido sobre texto | Búsqueda de palabras en documentos |
| **Espaciales**, **GIN/GiST** (PostgreSQL) | Datos geográficos, JSON, arrays | — |

**Coste de los índices**: ocupan espacio y **ralentizan las inserciones, actualizaciones y borrados**, porque hay que mantenerlos. Se crean en columnas usadas en WHERE, JOIN y ORDER BY con buena **selectividad**.

### 5.2. Recuperación de información y motores de búsqueda

Los **motores de búsqueda de texto** (*search engines*) permiten buscar en grandes volúmenes de **texto no estructurado** (documentos, informes clínicos, páginas web) de forma rápida y por **relevancia**, cosa que las bases de datos relacionales hacen mal (LIKE '%palabra%' no usa índices).

**El índice invertido**: la estructura central. En lugar de guardar, para cada documento, sus palabras, guarda **para cada término la lista de documentos** (y posiciones) donde aparece, como el índice analítico de un libro.

**Proceso de indexación (análisis del texto)**:

1. **Tokenización**: dividir el texto en palabras (*tokens*).
2. **Normalización**: pasar a minúsculas, quitar acentos.
3. Eliminación de **palabras vacías** (*stop words*: «el», «de», «y»).
4. **Lematización** o ***stemming***: reducir las palabras a su raíz («diagnósticos», «diagnosticar» → «diagnost»).
5. **Sinónimos** y tesauros (en sanidad, terminologías como **SNOMED CT**).

**Ordenación por relevancia**:

- **TF-IDF**: la relevancia aumenta con la **frecuencia del término en el documento** (TF) y disminuye si el término es **frecuente en toda la colección** (IDF).
- **BM25**: evolución de TF-IDF; el algoritmo por defecto de Lucene y Elasticsearch.
- **PageRank** (Google): relevancia según los **enlaces** que recibe una página.
- Hoy también **búsqueda semántica** con **vectores** (*embeddings*) generados por modelos de IA y bases de datos vectoriales, base del **RAG** (tema 30).

**Funciones habituales**: búsqueda booleana (AND, OR, NOT), por frases, con comodines, **difusa** (tolerante a errores de escritura), **facetada** (filtros por categorías), autocompletado, resaltado de los fragmentos, sugerencias.

**Herramientas**:

| Motor | Características |
|---|---|
| **Apache Lucene** | Biblioteca Java de indexación y búsqueda; base de los demás |
| **Elasticsearch** | Motor distribuido basado en Lucene, **API REST y JSON**, escalable; forma parte de la pila **ELK / Elastic Stack** (**Elasticsearch, Logstash, Kibana**, Beats), muy usada también para **centralizar y analizar registros** |
| **OpenSearch** | Bifurcación libre de Elasticsearch impulsada por AWS |
| **Apache Solr** | Motor basado en Lucene de la Fundación Apache |
| Funciones *full-text* de los SGBD | SQL Server Full-Text Search, Oracle Text, PostgreSQL (tsvector, tsquery) |

**Buscadores web**: rastreadores (*crawlers*) que recorren la web, indexación y ordenación. Para que los buscadores indexen o no un sitio se usan **robots.txt** y los **mapas del sitio (*sitemaps*)**.

## 6. El acceso a las bases de datos no relacionales

### 6.1. Bases de datos NoSQL

**NoSQL** («*Not only SQL*») agrupa bases de datos que **no usan el modelo relacional de tablas**, diseñadas para **grandes volúmenes**, **alta velocidad**, datos **semiestructurados** y **escalado horizontal** (añadiendo servidores). Los tipos (clave-valor, documentales, columnares, grafos) se detallan en el tema 22.

### 6.2. El teorema CAP y el modelo BASE

- **Teorema CAP** (Eric **Brewer**, 2000): un sistema distribuido **no puede garantizar a la vez** las tres propiedades:
  - **Consistencia (C)**: todos los nodos ven los mismos datos al mismo tiempo.
  - **Disponibilidad (A, *Availability*)**: toda petición recibe respuesta.
  - **Tolerancia a particiones (P)**: el sistema sigue funcionando aunque se corte la comunicación entre nodos.
  Como en una red las particiones son inevitables, hay que elegir entre **CP** (consistencia: MongoDB con configuración por defecto, HBase) y **AP** (disponibilidad: Cassandra, CouchDB, DynamoDB).
- **BASE** (frente a ACID): ***Basically Available*** (disponible básicamente), ***Soft state*** (estado flexible) y ***Eventual consistency*** (**consistencia eventual**: los nodos acaban siendo coherentes con el tiempo).

### 6.3. Formas de acceso

| Base de datos | Acceso |
|---|---|
| **MongoDB** (documental) | **Drivers oficiales** para cada lenguaje (Java, C#, Python, Node.js); documentos **JSON/BSON**; consultas como `db.pacientes.find({ edad: { $gt: 65 } })`; **canal de agregación** (*aggregation pipeline*: $match, $group, $sort); shell **mongosh**; Compass |
| **Redis** (clave-valor) | Órdenes simples (**SET**, **GET**, EXPIRE, estructuras de listas, conjuntos, *hashes*); clientes en todos los lenguajes; protocolo propio RESP |
| **Cassandra** (columnar) | **CQL** (*Cassandra Query Language*), de sintaxis parecida a SQL, pero sin JOIN; drivers |
| **Neo4j** (grafos) | **Cypher**: `MATCH (p:Paciente)-[:TRATADO_POR]->(m:Medico) RETURN p, m`; protocolo Bolt; drivers |
| **CouchDB** | **API REST HTTP** con JSON |
| **Elasticsearch** | **API REST** con consultas en JSON (Query DSL) |
| **Servicios en la nube** | SDK y API REST (DynamoDB, Cosmos DB) |
| **Mapeadores ODM** | El equivalente a los ORM para documentos: Mongoose (Node.js), **Spring Data MongoDB**, Hibernate OGM |

También hay acceso **multimodelo** y conectores que permiten consultar NoSQL con SQL (drivers JDBC/ODBC para MongoDB o Cassandra, Apache Drill, Presto/Trino) e integrarlo con herramientas de BI.

### 6.4. Persistencia políglota

Las aplicaciones modernas combinan varias bases de datos según el tipo de dato (**persistencia políglota**): por ejemplo, una relacional para los datos transaccionales del paciente, Redis como **caché** de sesiones, Elasticsearch para la **búsqueda** en informes y una documental para documentos clínicos en JSON (FHIR).

## 7. Ideas que más caen en el examen

> - Lenguajes **procedimentales** (álgebra relacional) / **no procedimentales** (cálculo relacional, SQL, QBE).
> - Álgebra relacional: **selección σ** (filas), **proyección π** (columnas), unión, diferencia, producto cartesiano (básicos); join, intersección, división (derivados).
> - **QBE**: consulta por ejemplo, gráfica (Zloof, IBM; Access).
> - **ODBC**: Microsoft, API en C, independiente del lenguaje y del SGBD; **Driver Manager**; **DSN**.
> - **JDBC**: Java; **Connection, Statement, PreparedStatement** (parámetros, evita la inyección SQL), **CallableStatement** (procedimientos), **ResultSet**; driver **tipo 4** = Java puro.
> - **ADO.NET** (.NET), **PDO** (PHP), DB-API (Python).
> - **ORM**: mapeo objeto-relacional; **JPA** (especificación) + **Hibernate** (implementación); **Entity Framework** (.NET); carga **perezosa**; problema **N+1**.
> - Índices: **B+** (por defecto, rangos), **hash** (igualdad), **bitmap** (baja cardinalidad), **agrupado** (uno por tabla).
> - Motores de búsqueda: **índice invertido**, *stemming*, palabras vacías, **TF-IDF / BM25**; **Lucene**, **Elasticsearch** (pila **ELK**), Solr.
> - **CAP** (Brewer): consistencia, disponibilidad y tolerancia a particiones: **solo dos**. **BASE**: consistencia **eventual**.
> - Acceso NoSQL: drivers, **APIs REST**, **CQL** (Cassandra), **Cypher** (Neo4j), consultas JSON (MongoDB).
