## 1. Frameworks para el desarrollo de aplicaciones

### 1.1. Concepto

Un **framework** (marco de trabajo) es una **estructura de software reutilizable** que proporciona una **arquitectura**, un conjunto de **bibliotecas**, **convenciones** y herramientas sobre las que se construye una aplicación. El desarrollador **rellena** los puntos de extensión con su código.

**Diferencia con una biblioteca**: con una **biblioteca**, **tu código la llama** cuando la necesita; con un **framework**, es el **framework el que llama a tu código** (**inversión de control**, «principio de Hollywood»: *no nos llames, nosotros te llamaremos*). Muchos frameworks aplican además la **inyección de dependencias** (el framework crea y suministra los objetos que necesita cada componente).

**Ventajas**: productividad (no se reinventa lo común: acceso a datos, seguridad, enrutamiento, validación), **estructura homogénea** y buenas prácticas, mantenibilidad, seguridad incorporada, comunidad y documentación. **Inconvenientes**: curva de aprendizaje, dependencia del framework y de sus versiones, cierta rigidez.

### 1.2. Principales frameworks

| Ámbito | Frameworks |
|---|---|
| **Java** (servidor) | **Spring** (Spring Framework, **Spring Boot** para crear aplicaciones y microservicios con configuración mínima, Spring MVC, Spring Data, Spring Security), **Jakarta EE** (antes Java EE: JSF, JPA, CDI, EJB, JAX-RS), Quarkus, Micronaut, Struts (antiguo) |
| **.NET** (C#) | **ASP.NET Core** (MVC, Razor Pages, Web API, Blazor), Entity Framework Core |
| **PHP** | **Laravel**, **Symfony**, CodeIgniter; CMS como Drupal y WordPress |
| **Python** | **Django** (completo, patrón MTV, con administración automática), **Flask** (ligero), **FastAPI** (APIs) |
| **Ruby** | Ruby on Rails |
| **JavaScript / Node.js** (servidor) | **Express**, **NestJS** (TypeScript, estructurado), Next.js (renderizado en servidor) |
| **Front-end** (cliente) | **Angular** (Google; **framework completo** con TypeScript, muy usado en la Administración), **React** (Meta; **biblioteca** de interfaces basada en componentes y DOM virtual), **Vue.js**, Svelte |
| **Móvil multiplataforma** | **Flutter** (Dart, Google), **React Native**, .NET MAUI, Ionic |
| **CSS** | Bootstrap, Tailwind CSS |
| **Pruebas** | JUnit, Jest, Cypress (tema 29) |

En la Administración española son habituales **Java con Spring** y **Angular**, y existen marcos propios de algunas Administraciones.

## 2. MVC (Modelo-Vista-Controlador)

### 2.1. Concepto

El **Modelo-Vista-Controlador** es un **patrón de arquitectura** que **separa** una aplicación en **tres componentes** con responsabilidades distintas. Lo describió **Trygve Reenskaug** en **1979** para Smalltalk, en Xerox PARC.

| Componente | Responsabilidad |
|---|---|
| **Modelo** | Los **datos** y la **lógica de negocio** (reglas, validaciones, acceso a la base de datos). No sabe nada de cómo se presentan los datos |
| **Vista** | La **presentación**: muestra los datos del modelo al usuario (páginas HTML, pantallas, plantillas). No contiene lógica de negocio |
| **Controlador** | **Recibe las peticiones** o acciones del usuario, **invoca al modelo** y **selecciona la vista** que mostrará el resultado. Hace de **intermediario** |

### 2.2. Funcionamiento en una aplicación web

1. El usuario hace una **petición** (pulsa «Buscar paciente»): el navegador envía una petición HTTP.
2. El **controlador** la recibe (según la URL, mediante el **enrutador**).
3. El controlador pide al **modelo** los datos (el modelo consulta la base de datos y aplica las reglas).
4. El controlador pasa los datos a la **vista** adecuada.
5. La **vista** genera la respuesta (HTML o JSON) que se devuelve al navegador.

### 2.3. Ventajas

- **Separación de responsabilidades**: código más **organizado, mantenible y probable** (se puede probar el modelo sin interfaz).
- **Reutilización**: el mismo modelo con **varias vistas** (web, móvil, API).
- **Trabajo en paralelo** de diseñadores (vistas) y programadores (modelo y controladores).

### 2.4. Variantes

| Patrón | Diferencia |
|---|---|
| **MVP** (Modelo-Vista-Presentador) | El **presentador** contiene toda la lógica de presentación y la vista es pasiva (aplicaciones de escritorio, Android antiguo) |
| **MVVM** (Modelo-Vista-VistaModelo) | El **VistaModelo** expone los datos y comandos a la vista mediante **enlace de datos (*data binding*)** bidireccional (WPF, Angular, Vue, Knockout) |
| **MTV** (Modelo-Plantilla-Vista) | Nombre del MVC en **Django**: la «vista» hace de controlador y la «plantilla» (*template*) de vista |
| **Front controller** | Un único controlador de entrada que distribuye las peticiones (Spring DispatcherServlet) |

## 3. Aplicaciones web

### 3.1. Concepto y características

Una **aplicación web** es una aplicación que se **ejecuta en un servidor** y a la que los usuarios acceden mediante un **navegador** a través de una red (Internet o intranet), usando el protocolo **HTTP/HTTPS**.

**Ventajas**: **no requieren instalación** en el cliente (solo un navegador), **multiplataforma**, **actualización centralizada** (todos usan la última versión), acceso desde cualquier lugar. **Inconvenientes**: dependencia de la red y del servidor, rendimiento y acceso al hardware local más limitados (aunque las tecnologías modernas lo reducen), exposición a ataques web.

### 3.2. El protocolo HTTP

- **HTTP** (*HyperText Transfer Protocol*) es un protocolo de **aplicación**, de tipo **petición-respuesta** y **sin estado** (cada petición es independiente). **HTTPS** es HTTP sobre **TLS** (cifrado, puerto **443**; HTTP usa el **80**).
- Versiones: HTTP/1.1, **HTTP/2** (multiplexación, binario) y **HTTP/3** (sobre QUIC/UDP).
- **Métodos (verbos)**: **GET** (obtener un recurso), **POST** (enviar datos, crear), **PUT** (reemplazar o crear), **PATCH** (modificar parcialmente), **DELETE** (eliminar), HEAD, OPTIONS. GET, PUT y DELETE son **idempotentes** (repetirlos produce el mismo efecto).
- **Códigos de estado**:

| Rango | Significado | Ejemplos |
|---|---|---|
| **1xx** | Informativo | 100 Continue |
| **2xx** | **Éxito** | **200 OK**, **201 Created**, 204 No Content |
| **3xx** | **Redirección** | **301** Moved Permanently, **302** Found, 304 Not Modified |
| **4xx** | **Error del cliente** | **400** Bad Request, **401 Unauthorized** (no autenticado), **403 Forbidden** (sin permiso), **404 Not Found**, 405 Method Not Allowed, 409 Conflict, 429 Too Many Requests |
| **5xx** | **Error del servidor** | **500 Internal Server Error**, 502 Bad Gateway, **503 Service Unavailable**, 504 Gateway Timeout |

- **Cabeceras** (Content-Type, Authorization, Cache-Control, Set-Cookie…).
- **Gestión del estado**: como HTTP no guarda estado, se usan **cookies**, **sesiones** en el servidor (identificadas por una cookie) o **tokens** (por ejemplo **JWT**, *JSON Web Token*, firmados y enviados en cada petición).

### 3.3. Componentes de una aplicación web

- **Cliente**: el **navegador** (HTML, CSS, JavaScript).
- **Servidor web**: atiende las peticiones HTTP y sirve el contenido estático: **Apache HTTP Server**, **Nginx**, **IIS** (Microsoft).
- **Servidor de aplicaciones**: ejecuta la lógica del servidor: **Apache Tomcat**, **WildFly/JBoss**, WebLogic, WebSphere (Java), **Kestrel/IIS** (.NET), PHP-FPM, Node.js.
- **Base de datos**.
- **Proxy inverso** y **balanceador de carga** (Nginx, HAProxy, F5) que reparte las peticiones entre varios servidores y termina el TLS.
- **CDN** (red de distribución de contenidos) para el contenido estático.

### 3.4. Tipos de aplicaciones web

- **Multipágina (MPA)**: cada acción carga una **página nueva** generada en el servidor.
- **De una sola página (SPA, *Single Page Application*)**: se carga una página y después la aplicación **actualiza dinámicamente** el contenido con JavaScript, pidiendo datos (JSON) al servidor mediante **APIs** (Angular, React, Vue). Experiencia más fluida.
- **Renderizado en el servidor (SSR)** e híbridos (Next.js, Nuxt).
- **Aplicaciones web progresivas (PWA)**: ver apartado 5.4.

## 4. Principales arquitecturas de aplicaciones basadas en web

### 4.1. Arquitectura cliente-servidor

El **cliente** solicita servicios y el **servidor** los presta. Según cómo se reparten las funciones (presentación, lógica, datos) en **capas** lógicas (*layers*) y **niveles** físicos (*tiers*):

| Arquitectura | Distribución | Notas |
|---|---|---|
| **Una capa** | Todo en un mismo equipo | Aplicaciones de escritorio aisladas |
| **Dos capas** | **Cliente** (presentación y a menudo lógica: «cliente pesado») + **servidor de base de datos** | Aplicaciones clásicas de los años 90 |
| **Tres capas** | **Presentación** (navegador o cliente) + **lógica de negocio** (servidor de aplicaciones) + **datos** (servidor de base de datos) | **La arquitectura típica de las aplicaciones web**; más escalable y segura (el cliente no accede directamente a la base de datos) |
| **N capas** | Más divisiones (servicios, integración, caché…) | Grandes sistemas |

Cliente **ligero** (*thin client*: casi toda la lógica en el servidor, como un navegador) frente a cliente **pesado** (*fat client*).

### 4.2. Arquitectura orientada a servicios (SOA)

- Organiza el sistema como un conjunto de **servicios** **reutilizables**, **débilmente acoplados**, **autónomos** y **sin estado**, que exponen **funcionalidades de negocio** mediante **interfaces bien definidas** (contratos) y que se **combinan** (orquestación y coreografía) para construir los procesos.
- Tecnologías típicas:
  - **Servicios web SOAP**: mensajes en **XML** con el protocolo **SOAP** (sobre HTTP), descritos con **WSDL** (*Web Services Description Language*), con estándares de seguridad **WS-Security** y transacciones.
  - **Bus de servicios empresarial (ESB)**: plataforma central de **integración** que enruta, transforma (por ejemplo, de un formato a otro) y orquesta los mensajes entre servicios y aplicaciones (MuleSoft, WSO2, IBM Integration Bus, Oracle Service Bus). En sanidad, los **motores de integración** (Rhapsody, Mirth, Ensemble) cumplen un papel parecido con mensajes **HL7**.
  - Registro de servicios (UDDI, poco usado).
- **Ventajas**: **reutilización**, **interoperabilidad** entre sistemas heterogéneos, alineación con el negocio. **Inconvenientes**: complejidad, el ESB puede convertirse en un cuello de botella y punto central de fallo.

### 4.3. Microservicios

- La aplicación se divide en **servicios pequeños**, cada uno centrado en **una capacidad de negocio** concreta (pacientes, citas, facturación), que se **desarrollan, despliegan y escalan de forma independiente**, y se comunican mediante **APIs ligeras** (normalmente **REST/JSON** o gRPC) o **mensajería asíncrona** (eventos con **Kafka**, RabbitMQ).
- **Características**:
  - Cada microservicio tiene **su propia base de datos** (no se comparten las bases de datos).
  - **Equipos autónomos** responsables de cada servicio («quien lo construye, lo opera»).
  - **Despliegue independiente** y continuo (**CI/CD**), normalmente en **contenedores** (Docker) orquestados con **Kubernetes**.
  - **Tecnología heterogénea** (cada servicio puede usar el lenguaje más adecuado).
  - **Tolerancia a fallos** (si falla uno, no cae todo: patrones *circuit breaker*, reintentos).
- **Componentes de apoyo**: **pasarela de API (*API Gateway*)** (punto de entrada único que enruta, autentica, limita el tráfico), **descubrimiento de servicios**, **configuración centralizada**, **malla de servicios** (*service mesh*: Istio), **observabilidad** (registros centralizados, métricas, **trazas distribuidas**).
- **Ventajas**: **escalabilidad** selectiva, **agilidad** (despliegues frecuentes), **resiliencia**, equipos independientes. **Inconvenientes**: **complejidad operativa** (muchos servicios que desplegar y vigilar), comunicaciones por red (latencia), **consistencia de los datos** distribuidos (transacciones distribuidas, patrón Saga), pruebas de integración más difíciles.

| | **Monolito** | **SOA** | **Microservicios** |
|---|---|---|---|
| Unidad de despliegue | Una sola aplicación | Servicios empresariales grandes | Muchos servicios pequeños |
| Comunicación | Llamadas internas | **ESB**, SOAP/XML | APIs REST ligeras, eventos |
| Datos | Una base de datos | A menudo compartida | **Una por servicio** |
| Escalado | Todo junto | Por servicio | Por servicio, muy fino |

### 4.4. Otros modelos

- **Monolito**: toda la aplicación en un único despliegue. Sencillo al principio; difícil de mantener y escalar cuando crece. Variante recomendada: **monolito modular**.
- **Arquitectura en capas** (presentación, aplicación, dominio, infraestructura) y **arquitecturas limpias** (hexagonal o de puertos y adaptadores, *clean architecture*): el núcleo de negocio no depende de la tecnología.
- **Arquitectura orientada a eventos (EDA)**: los componentes se comunican **publicando y suscribiéndose a eventos** de forma asíncrona (Kafka).
- **Sin servidor (*serverless*, FaaS)**: el código se ejecuta en **funciones** que se activan ante eventos y escalan automáticamente; el proveedor gestiona la infraestructura (AWS Lambda, Azure Functions).
- **APIs REST** como contrato entre el *front-end* y el *back-end*, y entre sistemas.
- **Peer-to-peer** y arquitecturas **distribuidas**.

### 4.5. REST y otros estilos de API

**REST** (*Representational State Transfer*) es un **estilo de arquitectura** definido por **Roy Fielding** en su tesis doctoral (**2000**), muy usado para crear **APIs web**:

- Todo es un **recurso** identificado por una **URI** (/pacientes/123/citas).
- Se opera con los **métodos HTTP** estándar (GET para leer, POST para crear, PUT/PATCH para modificar, DELETE para borrar).
- **Sin estado**: cada petición contiene toda la información necesaria.
- **Representaciones** del recurso, normalmente en **JSON** (también XML).
- **Interfaz uniforme**, **cacheable**, sistema **en capas**, cliente-servidor; idealmente **HATEOAS** (las respuestas incluyen enlaces a las acciones posibles).
- Documentación con **OpenAPI** (antes **Swagger**). Seguridad con **OAuth 2.0** y tokens.
- El estándar sanitario **HL7 FHIR** es una API REST (tema 34).

Alternativas: **SOAP** (más formal, con WSDL y estándares WS-*), **GraphQL** (el cliente **pide exactamente los campos** que necesita en una sola consulta; Meta), **gRPC** (llamadas remotas binarias de alto rendimiento con Protocol Buffers; Google), **WebSockets** (comunicación bidireccional en tiempo real).

## 5. Desarrollo web front-end y en servidor, multiplataforma y multidispositivo

### 5.1. Front-end y back-end

| | **Front-end** (lado del cliente) | **Back-end** (lado del servidor) |
|---|---|---|
| Qué es | La parte con la que **interactúa el usuario**, que se ejecuta en el **navegador** | La parte que se ejecuta en el **servidor**: **lógica de negocio**, **acceso a datos**, seguridad, integración |
| Tecnologías | **HTML**, **CSS**, **JavaScript / TypeScript**, frameworks (**Angular**, React, Vue), WebAssembly | **Java** (Spring), **C#** (.NET), **PHP**, **Python**, **Node.js**, Go; bases de datos, servidores, APIs |
| Preocupaciones | **Usabilidad**, **diseño adaptativo**, **accesibilidad**, rendimiento en el navegador | **Seguridad**, rendimiento, escalabilidad, integridad de los datos |

**Desarrollador *full-stack***: el que trabaja en ambas partes. Pilas típicas: **LAMP** (Linux, Apache, MySQL, PHP), **MEAN** (MongoDB, Express, Angular, Node.js), **MERN** (con React), Java + Spring + Angular + Oracle/PostgreSQL.

### 5.2. Diseño adaptativo (*responsive*) y multidispositivo

- El **diseño web adaptativo** (*responsive web design*, Ethan Marcotte, 2010) hace que una misma web **se adapte automáticamente al tamaño de la pantalla** (móvil, tableta, escritorio) mediante:
  - **Rejillas fluidas** (anchos en porcentajes y unidades relativas).
  - **Imágenes flexibles**.
  - **Media queries** de CSS (estilos distintos según el ancho de la pantalla).
  - La etiqueta **meta viewport**.
- Enfoque ***mobile first***: diseñar primero para el móvil y ampliar después.
- Maquetación moderna con **CSS Flexbox** y **CSS Grid**.
- **Accesibilidad**: obligatoria en el sector público (**RD 1112/2018**, que transpone la Directiva (UE) 2016/2102; norma **UNE-EN 301549**, que remite a las pautas **WCAG 2.1 nivel AA** del W3C): textos alternativos, contraste, navegación con teclado, estructura semántica, compatibilidad con lectores de pantalla.

### 5.3. Desarrollo multiplataforma para móviles

| Enfoque | Descripción | Ejemplos | Ventajas / inconvenientes |
|---|---|---|---|
| **Nativo** | Una aplicación distinta para cada plataforma, con sus lenguajes y herramientas | **Kotlin**/Java (Android), **Swift** (iOS) | Máximo rendimiento y acceso al dispositivo / doble desarrollo |
| **Multiplataforma nativo o compilado** | Un único código que se compila o renderiza de forma nativa en varias plataformas | **Flutter** (Dart), **React Native** (JavaScript), **.NET MAUI** (C#, antes Xamarin), Kotlin Multiplatform | Un solo código, buen rendimiento / dependencia del framework |
| **Híbrido** | Aplicación web (HTML, CSS, JavaScript) empaquetada dentro de un contenedor nativo (*WebView*) | **Ionic**, Apache Cordova / Capacitor | Reutiliza tecnologías web / menor rendimiento |
| **Web adaptativa y PWA** | Una web que funciona en cualquier dispositivo | — | Sin tiendas ni instalación / acceso limitado al hardware (cada vez menos) |

### 5.4. Aplicaciones web progresivas (PWA)

Una **PWA** (*Progressive Web App*) es una **aplicación web** que ofrece una experiencia **parecida a una aplicación nativa**:

- Se puede **instalar** en la pantalla de inicio (con un fichero **manifiesto** web).
- **Funciona sin conexión** o con mala conexión gracias a los ***service workers*** (*scripts* que interceptan las peticiones y gestionan una **caché**).
- Puede recibir **notificaciones *push***.
- Requiere **HTTPS**.
- Se actualiza sola y no necesita pasar por las tiendas de aplicaciones.

## 6. Lenguajes: HTML, XML y sus derivaciones

### 6.1. HTML

- **HTML** (*HyperText Markup Language*) es el **lenguaje de marcado** que define la **estructura y el contenido** de las páginas web mediante **etiquetas** (`<p>`, `<a href>`, `<img>`, `<table>`, `<form>`). Lo creó **Tim Berners-Lee** (CERN, **1991**). Hoy lo mantiene el **WHATWG** como **estándar vivo** (*HTML Living Standard*), en colaboración con el **W3C**.
- **HTML5** (2014) introdujo:
  - **Etiquetas semánticas**: `<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<aside>`, `<footer>` (mejoran la **accesibilidad** y el posicionamiento).
  - **Multimedia nativa**: `<video>`, `<audio>` (sin complementos como Flash).
  - **Gráficos**: `<canvas>` y **SVG** integrado.
  - **Formularios** mejorados (tipos email, date, number; validación).
  - **APIs** de JavaScript: almacenamiento local (localStorage, IndexedDB), geolocalización, arrastrar y soltar, *Web Workers*, **WebSockets**, *service workers*.
- **CSS** (*Cascading Style Sheets*, hojas de estilo en cascada): define la **presentación** (colores, tipografías, disposición); separa el contenido (HTML) de la presentación (CSS). **CSS3**: módulos como Flexbox, Grid, animaciones, *media queries*. Preprocesadores: Sass, Less.
- **DOM** (*Document Object Model*): representación en **árbol** del documento HTML que JavaScript puede leer y modificar dinámicamente.

### 6.2. XML

- **XML** (*eXtensible Markup Language*), recomendación del **W3C** de **1998**, derivado de **SGML**. Es un **metalenguaje**: sirve para **definir lenguajes de marcado** propios, para **estructurar, almacenar e intercambiar datos** de forma independiente de la plataforma. Las etiquetas **no están predefinidas**: las define cada aplicación.

```
<?xml version="1.0" encoding="UTF-8"?>
<paciente nhc="123">
  <nombre>Ana López</nombre>
  <fechaNacimiento>1980-05-12</fechaNacimiento>
</paciente>
```

- **Documento bien formado**: cumple las **reglas sintácticas** de XML: un **único elemento raíz**; todas las etiquetas **cerradas**; **correctamente anidadas**; distingue **mayúsculas y minúsculas**; valores de los atributos **entre comillas**; caracteres especiales escapados (&lt; &amp;).
- **Documento válido**: además de estar bien formado, **cumple las reglas de una gramática** que define qué elementos y atributos puede tener y en qué orden:
  - **DTD** (*Document Type Definition*): la forma clásica, con sintaxis propia no XML y pocos tipos de datos.
  - **XML Schema (XSD)**: escrito en XML, con **tipos de datos** (fechas, números, patrones) y más potencia. La forma recomendada.
  - Otros: RELAX NG, Schematron.
- **Espacios de nombres (*namespaces*)**: evitan conflictos entre etiquetas de distintos vocabularios (xmlns).
- **Analizadores (*parsers*)**: **DOM** (carga todo el documento en memoria como un árbol) y **SAX** (lectura secuencial por eventos, para documentos grandes); StAX.

### 6.3. Derivaciones y tecnologías relacionadas con XML

| Tecnología | Función |
|---|---|
| **XHTML** | HTML reformulado como **XML** (más estricto: bien formado) |
| **XSL / XSLT** | **Transformar** documentos XML en otros formatos (otro XML, HTML, texto) |
| **XSL-FO** | Formatear XML para impresión (generar PDF) |
| **XPath** | Lenguaje para **navegar y seleccionar** partes de un documento XML (/paciente/nombre) |
| **XQuery** | Lenguaje de **consulta** sobre datos XML |
| **XLink / XPointer** | Enlaces |
| **SVG** | Gráficos **vectoriales** en XML |
| **MathML** | Fórmulas matemáticas |
| **RSS** y **Atom** | Sindicación de contenidos (noticias) |
| **SOAP** y **WSDL** | Servicios web |
| **SAML** | Intercambio de **aserciones de autenticación** (federación de identidades, SSO) |
| **XAdES** | **Firma electrónica** en XML |
| **XBRL** | Información financiera |
| **HL7 CDA** | **Documentos clínicos** (tema 34) |
| **OOXML** y **ODF** | Documentos ofimáticos (ficheros ZIP con XML) |
| **KML/GML** | Información geográfica |

### 6.4. JSON y otros formatos

- **JSON** (*JavaScript Object Notation*, Douglas Crockford, norma ECMA-404 / RFC 8259): formato de intercambio de datos **ligero**, basado en **objetos** (pares clave-valor entre llaves) y **arrays**; más compacto y fácil de procesar que XML; el **estándar de facto** de las **APIs REST** (y de FHIR). Se valida con **JSON Schema**.
- **YAML**: formato legible para **configuración** (Kubernetes, Ansible, CI/CD).
- **Markdown**: marcado ligero para documentación.

## 7. Navegadores y lenguajes de programación web

### 7.1. Navegadores web

Un **navegador** es la aplicación que **solicita, recibe, interpreta y muestra** el contenido web. Componentes: **motor de renderizado** (interpreta HTML y CSS y dibuja la página), **motor de JavaScript**, interfaz de usuario, red, almacenamiento, seguridad (aislamiento de sitios, *sandbox*).

| Navegador | Empresa | Motor de renderizado | Motor de JavaScript |
|---|---|---|---|
| **Google Chrome** | Google | **Blink** (bifurcación de WebKit) | **V8** |
| **Microsoft Edge** | Microsoft (desde 2020 basado en **Chromium**) | **Blink** | V8 |
| Opera, Brave, Vivaldi | — | Blink | V8 |
| **Mozilla Firefox** | Mozilla | **Gecko** | **SpiderMonkey** |
| **Safari** | Apple | **WebKit** | JavaScriptCore |
| Internet Explorer (retirado en 2022) | Microsoft | Trident | Chakra |

**Chromium** es el proyecto de código abierto base de Chrome y Edge. Las organizaciones gestionan los navegadores de forma centralizada (políticas por **GPO**, extensiones permitidas, actualizaciones) y deben probar sus aplicaciones en los navegadores corporativos.

### 7.2. Lenguajes de programación web

**En el cliente (navegador)**:

- **JavaScript**: el **lenguaje de programación de la web en el cliente**, creado por **Brendan Eich** (Netscape, **1995**) y normalizado como **ECMAScript** (ECMA-262; ES6/ES2015 supuso un gran salto: clases, módulos, funciones flecha, promesas). Interpretado y compilado **JIT**, de tipado **dinámico**, orientado a eventos y asíncrono (**promesas**, `async/await`). Manipula el **DOM**, responde a **eventos** y se comunica con el servidor (**AJAX**, **Fetch API**). No tiene relación con Java salvo el nombre.
- **TypeScript** (Microsoft, 2012): **superconjunto de JavaScript con tipado estático**, que se **transpila** a JavaScript; muy usado en aplicaciones grandes (obligatorio en Angular).
- **WebAssembly (Wasm)**: formato binario que permite ejecutar en el navegador código compilado de C, C++, Rust o C# (Blazor) con rendimiento casi nativo.

**En el servidor**:

- **Java** (servlets, JSP, Spring), **C#** (**ASP.NET Core**), **PHP**, **Python**, **Ruby**, **Go** y **JavaScript en el servidor con Node.js** (entorno de ejecución basado en el motor V8, con modelo **asíncrono** de un solo hilo y bucle de eventos; gestor de paquetes **npm**).
- Antiguos: **CGI** (programas externos invocados por el servidor web), ASP clásico, ColdFusion.

## 8. Lenguajes de script

### 8.1. Concepto

Un **lenguaje de *script*** (de guiones) es un lenguaje, normalmente **interpretado** y de **tipado dinámico**, pensado para **automatizar tareas**, **controlar otras aplicaciones** o **añadir comportamiento** a un entorno (una página web, un sistema operativo, una aplicación). Sus programas, los ***scripts***, suelen ser **cortos** y se ejecutan **sin compilación previa**.

### 8.2. Clasificación

| Tipo | Se ejecuta en | Lenguajes | Usos |
|---|---|---|---|
| **De cliente (*client-side*)** | El **navegador** del usuario | **JavaScript** (y TypeScript transpilado) | Validar formularios antes de enviarlos, interactividad, animaciones, actualizar partes de la página, SPA |
| **De servidor (*server-side*)** | El **servidor web**, que genera la respuesta antes de enviarla | **PHP**, **Python**, **Node.js**, Ruby, Perl, ASP | Acceso a bases de datos, autenticación, generar páginas dinámicas |
| **De sistema / *shell*** | El **sistema operativo** | **Bash** (Linux), **PowerShell** (Windows y multiplataforma), CMD/batch, VBScript (obsoleto, en retirada en Windows) | **Administración**, automatización de tareas, copias, despliegues |
| **De propósito general y pegamento** | Cualquier entorno | **Python**, Perl, Ruby, Lua | Automatización, procesado de datos, integración |
| **Embebidos en aplicaciones** | Dentro de otra aplicación | VBA (Office), Apps Script (Google), Lua (juegos) | Macros, extensiones |

> **Diferencia clave**: los **scripts de cliente** se ejecutan en el **navegador** (el usuario puede ver y modificar el código, por lo que **nunca** deben ser la única validación de seguridad), mientras que los **de servidor** se ejecutan en el **servidor** (el usuario solo recibe el resultado).

### 8.3. Ventajas e inconvenientes

- **Ventajas**: **desarrollo rápido**, sin compilación, portables, fáciles de aprender, ideales para **automatizar** y para «pegar» sistemas.
- **Inconvenientes**: rendimiento menor que los compilados (aunque el JIT lo reduce), errores que solo aparecen al ejecutar, riesgos de **seguridad** (ejecución de *scripts* maliciosos: **XSS** en la web, *scripts* de PowerShell en los ataques), por lo que conviene **firmar** los *scripts*, restringir su ejecución (políticas de ejecución de PowerShell, AppLocker) y validar todas las entradas.

### 8.4. Seguridad en el desarrollo web

Las vulnerabilidades más comunes las recoge el **OWASP Top 10** (2021): control de acceso roto, fallos criptográficos, **inyección** (SQL, órdenes), diseño inseguro, configuración insegura, componentes vulnerables y obsoletos, fallos de identificación y autenticación, fallos de integridad del software y los datos, fallos de registro y monitorización, y **SSRF**. Medidas: **validar y sanear todas las entradas**, **consultas parametrizadas**, **escapar las salidas** (contra el **XSS**, *Cross-Site Scripting*), tokens **anti-CSRF**, **HTTPS** en todo, cabeceras de seguridad (Content-Security-Policy, HSTS), autenticación robusta y gestión segura de sesiones, actualizar las dependencias, **WAF** y pruebas de seguridad (SAST, DAST) en la CI/CD.

## 9. Ideas que más caen en el examen

> - **Framework** (inversión de control: llama a tu código) frente a **biblioteca** (tu código la llama). Java: **Spring / Spring Boot**; .NET: **ASP.NET Core**; PHP: Laravel, Symfony; Python: **Django**; front-end: **Angular** (framework), **React** (biblioteca), Vue.
> - **MVC** (Reenskaug, 1979): **Modelo** (datos y lógica), **Vista** (presentación), **Controlador** (recibe peticiones y coordina). Variantes **MVP**, **MVVM** (*data binding*), **MTV** (Django).
> - HTTP sin estado; métodos **GET, POST, PUT, PATCH, DELETE**; códigos **2xx éxito**, **3xx redirección**, **4xx error del cliente** (401, 403, **404**), **5xx error del servidor** (**500**, 503).
> - Arquitectura de **tres capas**: presentación, lógica de negocio, datos.
> - **SOA**: servicios reutilizables y poco acoplados; **SOAP + WSDL**; **ESB**.
> - **Microservicios**: pequeños, **despliegue independiente**, **base de datos propia**, APIs REST, contenedores, **API Gateway**.
> - **REST** (Fielding, 2000): recursos con URI, métodos HTTP, **sin estado**, JSON; **OpenAPI/Swagger**. Alternativas: **GraphQL**, gRPC.
> - **Responsive**: rejillas fluidas, imágenes flexibles, **media queries**; *mobile first*. **PWA**: instalable, **sin conexión** (*service workers*), HTTPS. Multiplataforma: **Flutter**, React Native, .NET MAUI; híbridas: Ionic.
> - **HTML5**: etiquetas semánticas, video, audio, canvas. **CSS**: presentación. **DOM**: árbol del documento.
> - **XML** (W3C, 1998): metalenguaje. **Bien formado** (sintaxis correcta) frente a **válido** (cumple su **DTD** o **XSD**). **XSLT** (transformar), **XPath** (navegar), XQuery, **SVG**, SOAP, **SAML**, XAdES, **CDA**. **JSON**: estándar de las APIs REST.
> - Motores: **Blink** (Chrome, Edge), **Gecko** (Firefox), **WebKit** (Safari); **V8** (JavaScript de Chrome).
> - **JavaScript** = ECMAScript (cliente; **Node.js** en servidor); **TypeScript** = JavaScript con tipos.
> - *Scripts* **de cliente** (navegador: JavaScript) frente a **de servidor** (PHP, Python, Node.js) y **de sistema** (**Bash**, **PowerShell**).
> - Seguridad web: **OWASP Top 10**, inyección, **XSS**, CSRF, validar entradas.
